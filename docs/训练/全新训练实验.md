#### C. 字段分组释义（按用途看）

##### C.1 5 路 loss —— 4 路进 backward + 1 路只监控

**backward 实际公式**（`train_grpo_neg_sample.py:303`）

```
loss = 0.2 · gbpo_loss  +  1.0 · grpo_loss  +  1.5 · legal_loss  +  2.0 · prior_loss
```

| 字段 | 进 backward | 系数 | clip_ε | advantage 来源 | 业务含义 |
|------|:----------:|:---:|:------:|---------------|---------|
| `grpo_Loss` | ✅ | 1.0 | 0.2 | reward 模型预测 (`advantages`) | 主 RL：reward 高的候选概率被拉高 |
| `gbpo_Loss` | ✅ | 0.2 | 0.0 | 真实 ±1 (`gbpo_advantage`) | 真实正样本概率↑、负样本↓（监督） |
| `legal_Loss` | ✅ | 1.5 | 0.2 | 反解 0/1 (`decoding_advantages`) | 把模型从「乱写码本」拉回 |
| `prior_Loss` | ✅ | 2.0 | 0.2 | 先验偏置 (`prior_advantages`) | 抑制爆款扎堆、鼓励长尾 |
| `pt_Loss` | ❌ **只监控** | — | — | — | `-new_log_probs.mean()`，纯 NLL 温度计 |

**两点必须澄清**

| 字段 | 真相 | 训练流程文档为什么没写 |
|------|------|----------------------|
| `pt_Loss` | **不进 backward**（line 303 算完 `loss=...` 后才算 `pt_loss = compute_pt_loss(new_log_probs)`，从未加进 `loss`）。它只是当前 policy 对**真实曝光 URL** 的 NLL，用来看 RL 相对 SFT-302596 起点漂了多少 | 因为它不影响梯度，流程文档只列了真正训练的 4 路 |
| `prior_Loss` | **进 backward**（系数 2.0，权重最大），但 **log 行里没打印它**——要追 prior 贡献只能改代码或看 grad norm | print 行漏了，不是真不存在 |

> 一句话总结：**实际训练 = 4 路 loss 加权和**；`pt_Loss` 只是放在打印里的"漂移温度计"，`prior_Loss` 是"打了梯度但没打印"的隐形大权重。

##### C.2 样本组成

| 字段 | 含义 | 健康范围 |
|------|------|---------|
| `real_batch_size` | 实际用户数（一定 = 50） | 50 |
| `Uniq_ratio` | batch 内生成 url 去重比例 | 0.8 ~ 0.9 |
| `pos_num` / `neg_num` | 真实正/负样本数（按 `rl_label`） | 比 ~ 1:3 ~ 1:4 |

##### C.3 推荐质量（核心追踪项）

| 字段 | 含义 | 健康趋势 |
|------|------|---------|
| `AvgReward@5` | top-5 概率候选的平均 reward | **持续上升** |
| `AvgReward@3` | top-3 概率候选的平均 reward | **持续上升** |
| `Hitrate@G` | G=10 候选里命中真实曝光 url 的比例 | 0.01 ~ 0.05（不会很高，beam=10 vs 9.1M 词表） |
| `pos_prob` / `neg_prob` | 真实正/负样本的模型概率 | pos↑、neg↓，差距拉开是好 |

##### C.4 健康度（**最关键，崩盘前兆都在这**）

| 字段 | 含义 | 健康 | 崩盘前兆 | 已崩盘 |
|------|------|------|---------|--------|
| `EmptyDecodingRatio` | 整 batch 反解失败比例 | < 0.05 | > 0.2 | ≈ 1.0（整批 skip） |
| `Unique` | beam-G=10 内**不同** url 平均数 | 7 ~ 9 | < 4 | 1 ~ 2（生成全收敛同一条） |

##### C.5 AUC（评估当前 policy 对真实 like 的判别力）

| 字段 | 含义 |
|------|------|
| `LikeAUC` | 本 batch 更新**前**，模型对 like 标签的 AUC |
| `LikeAfterAUC` | 本 batch 更新**后**重新算一次 |
| `RewardLikeAUC` | reward 模型自身对 like 的 AUC（**reward 模型的上限**） |

> `RewardLikeAUC` 是 OneRec 永远追不过的天花板——因为 grpo 用它当老师。

#### D. 主要追的几个数（精简版）

| 优先级 | 字段 | 看什么 |
|-------|------|-------|
| ★★★ | `EmptyDecodingRatio` | 健康度第一指标，> 0.2 就要警觉 |
| ★★★ | `Unique` | 模型有没有扎堆，跌到 < 4 危险 |
| ★★ | `AvgReward@5` | 主优化目标，持续上升 |
| ★★ | `Hitrate@G` | 推荐质量 |
| ★ | 4 路 loss | 分解贡献，调试时看 |
| ★ | `LikeAUC` / `LikeAfterAUC` | 判别力是否提升 |

#### E. v12_new 实际崩盘签名

| 阶段 | `EmptyDecodingRatio` | `Unique` | `Hitrate@10` | 日志现象 |
|------|---------------------|---------|--------------|----------|
| 1000 ~ 4000 step | 健康 (~0.01-0.05) | 健康 (~7-9) | ~0.02 | 正常 |
| 4000+ step | 飙升 → ~1.0 | 跌到 1-2 | 0 | `Invalid ids length: 2`、`All samples decoded to empty URLs. Skipping batch.` |

#### F. 结论

RL 在 4000 step 后**反解率坍塌**——模型生成的 token 序列长度跌到 2（应为 3），整批 URL 解析不出，所有 batch 被 skip。**无可上线 ckpt**。崩盘签名是 `EmptyDecodingRatio ≈ 1.0` + `Unique ≈ 1-2`。

### 2.5 v12_new 总结

| 阶段 | 完成度 | 是否上线 | 备注 |
|------|--------|---------|------|
| PT | ✅ 272030 step | 作为 SFT 起点 | loss 7.52 → 3.65 |
| SFT | ✅ 至 302596 | 历史在线 | loss 在正样本分布下波动 3.4~5.3 |
| RL | ❌ 4000 step 后崩 | 未上线 | 反解失败，ckpt 不可用 |

整个 v12_new 路径已**冻结只读**，不再训练。

### 4.4 ⚠️ 为什么没有「跟老精排的离线对比」指标

> **结论先行**：**不是漏了，是范式天花板**——生成式 vs 判别式，最常用的离线指标（AUC / GAUC / NDCG@K）**结构上对不上**。这意味着 OneRec 的最终好坏**只能由在线 A/B 判**，业界（Meta HSTU、快手 OneRec）也都是这么做的。

#### A. 任务范式根本不同

| 模型 | 任务 | 输入 | 输出 |
|------|------|------|------|
| 老精排 | **判别式**打分 | 用户 + **给定候选 URL** 的特征 | (user, url) → score |
| OneRec | **生成式**生成 | 用户行为序列 | 直接 **decode 出 URL** |

#### B. 因此最常用的精排离线指标都套不上

| 维度 | 精排 | OneRec |
|------|------|--------|
| 候选池来源 | 上游召回**给定** | 模型自己**生成** |
| 离线 AUC 怎么算 | 拿真实 (user, url, label) 直接打分 | 模型不会给"不存在于词表里"的 url 算概率（UNK = 0） |
| NDCG / MRR | 给定候选列表排序 | 没有候选列表的概念 |
| Hitrate@K | 给定 K 条 rerank | beam 生成 K 条看命不命中（**不是一回事**） |

> 一句话：**精排离线指标的前提是"有候选"**；OneRec 的输入根本没有候选这一步，从根上算不出来。

#### C. 业界共识

| 系统 | 离线对比基线 | 真正判定 |
|------|-------------|---------|
| Meta HSTU | 自家代次对比，无跨范式 | **在线 A/B** |
| 快手 OneRec | 同上 | **在线 A/B** |
| 本项目 | 同上 | **在线 A/B** |

> 生成式推荐**最终结论必须在线判**，这是行业默认。OneRec 自带的 `Hitrate@G` / `AvgReward@K` / `LikeAUC` 只是**生成式专属的内部健康度代理**——它们衡量 OneRec 自己有没有学崩，**不衡量"是否比精排好"**。

#### D. 可补的几处（"真正漏的"少数）

| 漏 | 是否该补 | 难度 |
|----|---------|------|
| PT/SFT 阶段无 AUC（RL 才有 `LikeAUC`） | ✅ 该补——在 `train_pt.py` 启 `AUCMetric` | 低 |
| 主流程 `evaluate()` 被三引号注释 | ✅ 该恢复 | 极低 |
| reward 模型 vs 老精排 AUC 对比（两边都是判别式，**完全可对比**） | ✅ 该补 | 中 |
| 用 OneRec 给精排候选打分算 AUC | ⚠️ 不推荐——会被 UNK 拖死，不公平 | 中 |

#### E. 真要离线对比，可选方案（均有局限）

| 方案 | 做法 | 公平度 |
|------|------|--------|
| ① 同候选打分 | 取精排曝光候选，让 OneRec 算 `target_prob` 算 AUC | ❌ 偏低——OneRec ~64% 候选 UNK |
| ② 反过来 | OneRec 生成 K 条让精排打分排序 | ❌ 候选池就是 OneRec 选的，偏 OneRec |
| ③ **回放仿真**（最常用） | 重放历史日志，看 OneRec 会不会"召回"真实点击 url | ⚠️ 半公平，等价于 `Hitrate@G` 加强版 |
| ④ Reward 模型 vs 老精排 | 同份 (user, url, label) 算两边 AUC | ✅ 公平，但比的是 reward 不是 OneRec |

> 实操首选 ③；但**任何离线方案都不能替代在线 A/B**。

### 4.5 主流程「以为有但没有」的指标

| 你以为有 | 实际 |

#### 4.6.2 `final_valid` — tokenizer 字典命中率（**不是模型学习信号**）

##### A. 一句话

`final_valid` = batch 内 target URL 在 `url2tokens` 字典里**查得到**的比例。

##### B. 真正机制（code-walk）

```python
# parser/tokenizer.py:86-93
def encode(self, url: str, add_bos):
    tokens = self.url2tokens.get(url, [self.unk_token_id] * 3)
    #                                  ↑
    #                                  字典 miss → [1501, 1501, 1501] 全 UNK
```

```python
# model/decoder.py:420
final_valid = torch.where(masked_labels == 1501, 0., 1.).sum() / (seqs_len-1)
```

| 步骤 | 行为 |
|------|------|
| ① tokenizer 训练 | rqkmeans 对**某时刻**的 URL 快照聚类，落盘成 `url2tokens` 字典 |
| ② OneRec 训练 | target URL 走 `url2tokens.get(url, [1501]*3)` 查表 |
| ③ 命中 | 返回完整 3 元组 → label 合法 → 进 CE |
| ④ 未命中 | 返回 `[1501, 1501, 1501]` → CE 全跳过 |
| ⑤ `final_valid` | 统计 batch 内**命中样本数 / batch_size** |

##### C. 为什么不会是 1.0？

| 直觉 | 实际 |
|------|------|
| "rqkmeans 训了所有 URL" | 只训了**当时存在的** URL 快照 |
| "训练数据 URL 都在词表里" | ❌ 训练数据是**滚动 30 天最新曝光**，每天新增 URL 没进字典 |

> 核心错配：tokenizer 是**静态快照**，训练数据是**滚动新增**。差集 = UNK。

##### D. 典型值与解读

| 阶段 | 典型值 | 物理含义 |
|------|--------|---------|
| PT | 0.35 ~ 0.40 | **35-40% 的 target URL 在字典里**；其余 60-65% 全 UNK 不进梯度 |
| v12_new SFT | 0.003 ~ 0.005 | `sample_alive_rows` 物理删后只剩极少数强正样本进 batch |
| RL | **不用此指标** | 改看 `EmptyDecodingRatio`（模型输出反解失败率） |

##### E. PT 0.36 = "你以为训了 1024，实际只有 ~370 进梯度"

| 数字 | 含义 |
|------|------|
| `batch_size` | 1024 |
| `final_valid` | 0.36 |
| **实际反传样本数** | ≈ 1024 × 0.36 ≈ **370** |
| **沉默样本** | ≈ 654（target URL 全 UNK，CE 跳过） |

##### F. 实战诊断

| 现象 | 诊断 |
|------|------|
| 单点看一个数字 | ❌ 没意义（接近常数） |
| 每天 / 每周持续下滑 | ⚠️ 新 URL 累积，**该重训 tokenizer** |
| 跨实验对比下降 | ⚠️ tokenizer 更换后覆盖更差 |
| SFT 跟 PT 一样高 (~0.36) | ⚠️ `sample_alive_rows` 物理删没切对，相当于在跑 PT |
| 长期 < 0.3 | ⚠️ url2tokens 严重过期 |

##### G. 定位

| 属性 | 是 | 否 |
|------|----|----|
| 数据健康温度计 | ✅ | — |
| tokenizer 覆盖率监控 | ✅ | — |
| 模型学习动态信号 | — | ❌ 模型权重 NaN 它也照常算 |
| 每步盯着看 | — | ❌ 几乎不动 |

#### 4.6.3 `target_prob` — 模型对真实 url 的预测信心

**含义**：模型给真实曝光 url 的 3 层联合概率，**按合法 token 比例加权平均**（不是简单 mean）。

**算法**（decoder.py:412-422）

```python
# Step 1: 每条样本算 3 层联合概率
P_i = exp( log P(L1=真) + log P(L2=真) + log P(L3=真) )    # [B]

# Step 2: 每条样本算"有效层比例"
valid_i = (3 层里非 UNK 非 mask 的层数) / 3                 # [B]，取值 0, 1/3, 2/3, 1

# Step 3: 加权平均
target_prob = Σᵢ P_i × valid_i  /  Σᵢ valid_i
```

| 样本类型 | `valid_i` | 在均值里的权重 |
|---------|-----------|---------------|
| 3 层全合法 | 1.0 | 满 |
| 1 层 UNK | 2/3 | 2/3 |
| 2 层 UNK | 1/3 | 1/3 |
| 3 层全 UNK / 全 mask | 0 | 完全剔除 |

**典型值**

| 阶段 | 值 | 含义 |
|------|-----|------|
| step 0 | (1/1500)³ ≈ 3e-10 | 随机初始化，3 层联合概率几乎为 0 |
| PT 收敛 | 1e-4 ~ 1e-3 | 给真实 url 万分之几 ~ 千分之几概率 |
| SFT 收敛 | 1e-3 ~ 1e-2 | 只学正样本，更高 |
| 崩溃 | 长期 < 1e-6 | 模型坏了 |

> 词表 1500³ ≈ 3.4×10⁹ 种组合，1e-3 = 模型把概率质量压缩到几千条 url，已是很强的判别能力。

#### 4.6.4 为什么 step 0 显示 `target_prob: 0.000000000` 但 `final_valid: 0.3643`？

| 指标 | step 0 实际值 | 日志显示 | 原因 |
|------|--------------|---------|------|
| `target_prob` | (1/1500)³ ≈ 2.96e-10 | `0.000000000` | 日志 `%.9f` 格式，e-10 被四舍五入到 0 |
| `final_valid` | ~0.36 | `0.3643` | 是 token 计数比例，跟模型权重无关 |

**关键区别**

| 维度 | `target_prob` | `final_valid` |
|------|---------------|---------------|
| 看什么 | 模型预测概率 | token id 是否 UNK |
| 跟模型权重相关吗 | ✅ 相关 | ❌ 无关（模型 NaN 也照常算） |
| step 0 是否为 0 | 数值不是 0 (3e-10)，是显示精度问题 | 正常显示 0.36 |

**证据**：表里 `target_prob` 从 `0.000000000` (step 0) → `0.000573359` (step 271900)，不是突然"有"了 prob，而是值从 ~10⁻¹⁰ 涨到 ~10⁻⁴，跨过了 `%.9f` 的显示门槛。

#### 4.6.5 速查表

| 指标 | 层面 | 算法 | 健康参考 | 报警 |
|------|------|------|---------|------|
| `final_valid` | token 级 | `(3 层 token ≠ UNK 的样本数) / batch_size` | PT ~0.36 | 长期 < 0.3 |
| `target_prob` | 概率级 | `Σ P_i × valid_i / Σ valid_i`（加权均值） | PT 1e-4~1e-3<br>SFT 1e-3~1e-2 | 长期 < 1e-6 |
| `actual_loss` | loss 级 | CE + RL + CT + Aux 综合 | 收敛后 2.0~3.5 | 长期 > 5 不降 |
