## 1. 总览

### 1.1 数据源

| 项 | 值 |
|------|------|
| 数据路径 | `/mnt/video.rank.s101/{YYYYMMDD}/{YYYYMMDDHH}/*.gz` |
| 单文件格式 | CSV，gzip 压缩，**131 列**（`data_args.columns_def`） |
| 每 hour 文件数 | 约 20 个（按 splitter 分片） |
| 一天约 | ~480 个 gz |
| 行级过滤 | **无 `check_line`**（与主流程显著不同）—— 原始行原样进 parser |
| 三阶段是否共用同一份 gzip | ✅ **物理同一份**，靠 `done_spec` 各自独立扫 |

> ⚠️ **跟主流程最关键差异**：主流程 corpus 在 `/mnt_onerec_model/corpus/video.rank.s101.pos_neg/`（pos_neg 预处理过的 131 列文件，已过滤 77% 无交互样本），v12_new 直接吃 `/mnt/video.rank.s101/` 原始 hour 级日志，**没有 `check_line` 这一关**，所有筛选都压在 parser 里做。

### 1.2 三阶段一图速览

> **三阶段做的都是同一件事**：从原始曝光日志里**只保留对学习有用的样本**，把"用户无反馈 / 时长太短 / 业务来源不属白名单 / target URL 不在码本字典"这几类丢掉。
> 差异只在两点：① **保留条件**的宽窄（PT 最宽，RL 居中，SFT 最严）；② **筛除层级**（PT 在 token-CE 层跳过；SFT/RL 在样本行层物理删）。

```
原始 gzip 一行 (131 列)
   │
   │  ❌ 无 check_line —— v12_new 不在行入口预过滤
   │
   ▼
┌───────────────────────────────────────────────────────────────────┐
│  PtParser   保留：曝光全部行                                       │
│             筛除：target URL 在 tokenizer 字典里 UNK 的样本         │
│             层级：token-CE 跳过（ignore_index=1501），样本仍在 batch│
│             留存：行层 100%；**token 层实际反传 ~36%**             │
├───────────────────────────────────────────────────────────────────┤
│  SFTParser  保留：强正反馈（like ∪ follow）                        │
│             筛除：非 like/follow、dur<6s、sign 不在白名单、UNK 码本│
│             层级：`sample_alive_rows` 物理删行 + token-CE 双重     │
│             留存：行层 ~0.4%（**最严**）                            │
├───────────────────────────────────────────────────────────────────┤
│  RLParser   保留：任何有效交互（like ∪ follow ∪ zmtlink ∪ dislike  │
│                  ∪ up ∪ down ∪ manu）                              │
│             筛除：无交互、dur<6s、sign 不在白名单、UNK 码本        │
│             层级：`sample_alive_rows` 物理删行（UNK 也直接删行）   │
│             留存：行层 ~10-20%                                      │
│             额外：输出 rl_label + reward serving 列                │
└───────────────────────────────────────────────────────────────────┘
```

### 1.3 三阶段筛选策略对比表

| 维度 | PT | SFT | RL |
|------|----|-----|-----|
| **入口 parser** | `PtParser` | `SFTParser` | `RLParser` |
| **保留条件**（这一行就是 alive 定义）| 曝光全部行 | **like ∪ follow**（最严，强正反馈）| 任何有效交互（like ∪ follow ∪ zmtlink ∪ dislike ∪ up ∪ down ∪ manu）|
| **筛除条件 ①** dur<6s | — | ✅ 行级删 | ✅ 行级删 |
| **筛除条件 ②** sign 不在白名单 | — | ✅ 行级删 | ✅ 行级删 |
| **筛除条件 ③** target URL UNK（不在码本字典）| ✅ **token-CE 跳过**（样本仍在 batch）| ✅ token-CE 跳过 | ✅ **行级删**（额外更激进）|
| **筛除层级** | 仅 token 层 | **样本行 + token 双重** | **样本行（含 UNK）+ token 双重** |
| **额外返回** | — | — | `rl_label`（=positive 标记，给 GRPO 算 advantage）<br>reward serving 列（给 reward 服务打分用） |
| **行层留存率** | 100%（不删行）| ~0.4%（见 §3.4） | ~10-20%（看 corpus 当天活跃度） |
| **token 层有效率** | ~36%（≈ `final_valid`，UNK 跳过率的反面）| 0.003 ~ 0.005（行层已剧减 × token 层再剩 ~36%）| 不用此指标，看 `EmptyDecodingRatio` |

> **三个筛除条件的统一语义**：dur<6s = 用户没真看；sign 不在白名单 = 非主产品线流量；UNK 码本 = target URL 不在 tokenizer 字典（学不了）。三阶段判定标准一致，差别只在 **PT 把 UNK 留在 batch 让 CE 跳，SFT/RL 一刀切删行**。

### 1.4 `sign` 字段 + 白名单过滤详解

#### A. `sign` 是什么

| 项 | 值 |
|----|---|
| 在 gzip 里的位置 | **第 0 列**（`f001.sign`）|
| 字段类型 | 字符串，每条样本一个 |
| 实际取值 | `360_97286759` / `360_6453942f` / `360_26aafc3a` / `360_xxxx` / `panel_yyyy` / 第三方 / 测试 sign / ... |
| 含义 | 这条曝光是**从哪个产品线 / 哪个流量入口**来的 |

样例（131 列里第 0 列）：

```
sign            | uid    | url           | duration | like | follow | ...
360_97286759    | u_001  | http://...   | 12.3     | 1    | 0      | ...   ← 白名单内 ✅
360_6453942f    | u_002  | http://...   | 8.5      | 0    | 1      | ...   ← 白名单内 ✅
weibo_share_01  | u_003  | http://...   | 15.0     | 1    | 0      | ...   ← ❌ 不在白名单
test_traffic_02 | u_004  | http://...   | 9.2      | 1    | 0      | ...   ← ❌ 不在白名单
```

#### B. 白名单是哪 3 个

代码 `PtParser.__init__:24` 硬编码：

```python
self.valid_sign = {"360_97286759", "360_6453942f", "360_26aafc3a"}
```

这 3 个 sign 对应 v12_new 当时认可的 3 个主产品线（具体哪 3 个业务线没有代码注释）。

#### C. 「sign 不在白名单 → 删行」具体做的事

SFT/RL parser 的 `sample_alive_rows()`：

```python
in_whitelist = np.isin(arr[:, 0], list(self.valid_sign))   # bool[B]
valid = valid & in_whitelist                                # 不在白名单 → valid=0
arr   = arr[valid > 0.5, :]                                 # 物理删除整行
```

效果示意：

```
原始 batch (1024 行)
   │
   ├─ 360_97286759 行 ─ (其他条件通过) ─→ 保留 ✅
   ├─ 360_6453942f 行 ─ (其他条件通过) ─→ 保留 ✅
   ├─ weibo_share_01 行 ─────────────→ **整行删除** ❌
   ├─ test_traffic_02 行 ──────────────→ **整行删除** ❌
   ├─ 360_26aafc3a 行 ─ (其他条件通过) ─→ 保留 ✅
   └─ ...

batch 缩小 → 进 forward
```

> "整行删" = 删的是**这条用户的这一次曝光行为**，不是删某个字段。这个用户的其他曝光（如果 sign 在白名单）正常进训练。

#### D. 三阶段是否做此过滤

| 阶段 | 是否做 sign 白名单过滤 | 代码位置 |
|------|---------------------|---------|
| PT | ❌ 不做（PT 全留行）| — |
| SFT | ✅ 行级物理删 | `sft_parser.py:sample_alive_rows` |
| RL | ✅ 行级物理删 | `rl_parser.py:sample_alive_rows` |

两边判定逻辑**完全一样**（都继承 `PtParser.valid_sign`），只是发生位置不同：SFT 在「保留 like ∪ follow」之后再过白名单；RL 在「保留任何 action」之后再过白名单。

#### E. 为什么要剔除

| 进训练的坏处 | 原因 |
|------------|------|
| 分布漂移 | 第三方 / 测试流量的用户画像 + 曝光内容跟主产品线很不一样，混进去污染模型 |
| 噪声多 | 机器人、自动化测试、爬虫请求的 sign 也会落到日志 |
| 业务边界 | 模型上线只服务这 3 个产品线，所以训练也只用这 3 个的数据 |

## 2. PT 阶段 —— 不删行，靠 token-CE 跳 UNK

### 2.1 流程

```
batch_lines (1024 行)
   │
   ▼
┌──────────────────────────────────────────────┐
│  PtParser.parser()                            │
│                                                │
│  ① 切分成 numpy str 数组 (1024, 131)           │
│  ② 默认值填充空字符串                          │
│  ③ extract_features()                          │
│     ├─ preprocess_user_features                │
│     ├─ preprocess_logsess_features             │
│     ├─ preprocess_logqueue_features            │
│     ├─ preprocess_logreallike_features         │
│     └─ url_tokenizer.batch_encode              │
│        target URL 不在字典 → 编码成 [1501,1501,1501] (UNK)│
└──────────────────────────────────────────────┘
   │
   ▼
返回 batch (1024, ...)  ← batch_size 不变
   │
   ▼
forward + CE，UNK 位置自动跳过 (ignore_index=1501)
→ **实际反传 ~36%**
```

### 2.2 PT 怎么筛

| 项 | 做法 |
|----|------|
| 行层级（要不要丢一整行） | ❌ **不丢** —— 1024 行全进 forward |
| token 层级（UNK 码本怎么办）| ✅ **CE 自动跳过**（`ignore_index=1501`）|
| 等效效果 | batch 里 1024 行都过模型，但 CE 只对 ~36% 命中字典的 URL 算梯度 |

> **跟 SFT/RL 比，PT 不是「不筛」，而是把「未知码本」这一筛除条件从行层挪到了 token-CE 层**。同样的 UNK 样本：
> - PT：留在 batch，token-CE 跳过 → ~36% 反传
> - SFT/RL：直接 `sample_alive_rows` 删行 → 行层留存率本身就低
>
> 另外 PT 不做 dur<6s / sign 白名单过滤，是因为 PT 阶段只想学"曝光分布"这件事——任何曝光都算样本，反正 CE 会自动跳过学不动的 UNK。SFT/RL 是在挑"高质量教师样本"，所以要把弱信号、非主产品线的全删掉。

## 3. SFT 阶段 —— 物理删，只留强正反馈

### 3.1 流程

```
batch_lines (1024 行)
   │
   ▼
┌──────────────────────────────────────────────┐
│  SFTParser.parser()                           │
│                                                │
│  ① 切分成 numpy str 数组 (1024, 131)           │
│  ② sample_alive_rows()                         │
│     ├─ 算 like_label / follow_label             │
│     ├─ valid = max(like, follow)  ← **最严**    │
│     ├─ dur < 6s → valid = 0                    │
│     ├─ sign 不合法 → valid = 0                  │
│     └─ 返回 arr[valid > 0.5, :]                 │
│  ③ extract_features() （正常走父类逻辑）        │
└──────────────────────────────────────────────┘
   │
   ▼
返回 batch (~4, ...)  ← batch 暴跌到原始 0.4%
```

### 3.2 `sample_alive_rows()` —— SFT 版

```python
# sft_parser.py:50-167 简化
def sample_alive_rows(arr):
    dislike = (dislike == "1") ∪ (like_c == "1")
    like    = ((like == "1") ∪ (favorite == "1")) AND NOT dislike
    follow  = (follow == "1")

    # ⚠️ SFT 的 valid 比 RL 都窄：只要 like 或 follow
    positive = max(like, follow)
    valid    = positive

    # 时长 < 6s → invalid
    if duration < 6.0:
        valid = 0

    # sign 不在白名单 → invalid
    if sign not in valid_sign:
        valid = 0

    # 返回物理过滤后的子集
    return arr[valid > 0.5, :]
```

> `valid_sign` 白名单（硬编码在 `PtParser.__init__:24`，SFT/RL 都用）：`360_97286759`、`360_6453942f`、`360_26aafc3a`。

### 3.3 SFT 的 valid 为什么这么严

| 字段 | SFT 是否纳入 valid | 理由 |
|------|------------------|------|
| `like` (f029) ∪ `favorite` (f089) | ✅ 强正信号 | 明确喜欢 |
| `follow` (f032) | ✅ 强正信号 | 关注作者 = 强偏好 |
| `zmtlink`（authorpanel 等 5 个面板） | ❌ **代码里有但被注释掉** | 写过 `positive = max(like, follow, zmtlink)`，最终用了不带 zmtlink 的版本（`sft_parser.py:144-145`）—— 当时认为面板点击是弱信号，不够"教师质量" |
| `dislike` / `like_c` | ❌ 显式排除 | SFT 只学正反馈 |
| 完播 / 上滑 | ❌ | 同上，被认为是弱信号 |

> SFT 的目的是"用最干净的强正样本把 PT 拉成一个生成式推荐器"，所以只留**用户主动表达喜欢**的两类（like / follow），其余物理删除。

### 3.4 实测留存率（v12_new 真实日志）

```
batch_size = 10240（DDP 4 卡）或 20480（单卡）
final_valid ≈ 0.003 ~ 0.005
→ 进 forward 的样本数 ≈ 10240 × 0.004 = ~40 条
```

| 阶段 | `final_valid` | 含义 |
|------|--------------|------|
| PT | 0.3643 | ~36% 的 target URL 在 tokenizer 字典里 |
| SFT 起点（step 272100） | **0.0041** | × 0.011，是 PT 的 1/100 |

**为什么暴跌 100 倍？**

- `final_valid` = "**剩下的样本里**，target URL 命中字典的比例"
- 但 SFT 已经物理删了 99.6% 的非 like/follow 样本
- 剩下的少数强正反馈样本里，target URL 命中字典的比例本身也低
- 两层乘起来 → 0.36 × ~0.01 ≈ 0.004

> 详见 `全新训练实验.md §2.3` —— 从 PT 末 `final_valid=0.3663` 突跌到 SFT 起 `0.0041` 不是模型问题，是 SFT parser 在物理删行。

## 4. RL 阶段 —— 物理删 + target UNK 删

### 4.1 流程

```
batch_lines (50 行，real_batch_size=50)
   │
   ▼
┌──────────────────────────────────────────────┐
│  RLParser.parser()                            │
│                                                │
│  ① 切分成 numpy str 数组 (50, 131)             │
│  ② sample_alive_rows()                         │
│     ├─ 算 zmtlink / dislike / like / follow    │
│     ├─ valid = max(from_up, from_down, manu,   │
│     │           positive ∪ dislike)            │
│     │   ← 任何交互行为都算 valid               │
│     ├─ dur < 6s → valid = 0                    │
│     ├─ sign 不合法 → valid = 0                  │
│     ├─ target URL 反查 tokenizer = UNK → 0     │
│     │   ← **RL 独有的过滤**                    │
│     └─ 返回 (arr[valid], rl_label[valid])      │
│  ③ extract_features()                          │
└──────────────────────────────────────────────┘
   │
   ▼
返回 (batch, raw_serving_cols, rl_label)
```

### 4.2 RL valid 定义（最宽）

```python
# rl_parser.py:113-176 简化
def sample_alive_rows(arr):
    # 同 SFT 算各类标签...
    positive = max(like, follow, zmtlink)
    actions  = max(dislike, positive)
    valid    = max(from_up, from_down, manu, actions)   # ⚠️ 任何 action 都算

    # 时长 / sign 过滤同 SFT
    if duration < 6.0: valid = 0
    if sign not in valid_sign: valid = 0

    # ⚠️ RL 独有：target URL 反查 tokenizer，UNK 一律删
    url_code = tokenizer.batch_encode(target_urls, False)[:, 0]
    if url_code == UNK(1501):
        valid = 0

    rl_label = positive   # 给 GRPO 算 advantage 用
    return arr[valid > 0.5], rl_label[valid > 0.5]
```

### 4.3 RL valid 跟 SFT valid 对比

| valid 包含项 | SFT | RL |
|------------|:---:|:---:|
| like / favorite | ✅ | ✅ |
| follow | ✅ | ✅ |
| zmtlink（5 个面板） | ❌ | ✅ |
| dislike / like_c | ❌ | ✅（**dislike 也算 valid**，作为负样本进 GRPO） |
| 上滑 / 下滑 / manu | ❌ | ✅ |
| target URL 命中字典 | 不要求 | **✅ 强制要求** |

### 4.4 为什么 RL 要 target UNK 删

| 原因 | 说明 |
|------|------|
| RL 阶段做生成 + 反解 | reward 服务对生成的 URL 打分，若 target URL 不在词表 → 算 reward 没法对齐 |
| `Hitrate@G` 算法依赖反解 | beam 输出 token 序列 → 反解 URL → 比 target URL，target 都 UNK 了没法比 |
| 减少 GRPO 噪声 | 反解失败的样本会污染 advantage 估计 |

### 4.5 RL 额外输出

| 字段 | 类型 | 用途 |
|------|------|------|
| `processed_features` | dict[str, Tensor] | 模型 forward |
| `raw_serving_cols` | np.ndarray | reward 服务调用：`reward_service` 要原始字符串列做特征 |
| `rl_label` | np.ndarray | GRPO advantage 算 `gbpo_advantage` 用（正/负样本标记） |

### 4.6 与 reward 服务的衔接

```
RLParser.parser(batch=50)
   │
   ├─→ processed_features → OneRec policy.forward()
   │   └─→ beam-G=10 生成 url tokens → 反解 URL
   │
   ├─→ raw_serving_cols(50 × N列) → reward_service(10.177.75.200:9503)
   │   └─→ 每条 (user, generated_url) → score
   │
   └─→ rl_label(=positive 标记) → gbpo_loss 算真实 ±1 advantage
```

## 5. 三阶段共享同一份 gzip 的工程实现

### 5.1 `done_spec` 隔离机制

```
done_spec 命名格式：done.{corpus_days}days.{base_spec}
```

| 阶段 | `corpus_days` | `base_spec`（来自启动参数） | 完整 `done_spec` |
|------|---------------|---------------------------|----------------|
| PT  | 30 | `onerec_pt_lazy_decoder_256` | `done.30days.onerec_pt_lazy_decoder_256` |
| SFT | 7  | `onerec_sft_lazy_decoder_256` | `done.7days.onerec_sft_lazy_decoder_256` |
| RL  | 1  | `onerec_rl_lazy_decoder_256` | `done.1days.onerec_rl_lazy_decoder_256` |

### 5.2 三阶段如何互不干扰

```
原始 gzip 一份（/mnt/video.rank.s101/20250901/2025090118/*.gz）
   │
   ├──── PT 跑完  → touch *.done.30days.onerec_pt_lazy_decoder_256
   │
   ├──── SFT 跑完 → touch *.done.7days.onerec_sft_lazy_decoder_256
   │
   └──── RL 跑完  → touch *.done.1days.onerec_rl_lazy_decoder_256
```

`PtDataset._get_train_file_names` (line 96-99) 在加载文件前会过滤：

```python
done_dirs = filter(
    lambda x: os.path.exists(x) and (not os.path.exists(f"{x}.{self.done_spec}")),
    done_dirs
)
```

即 "**带本阶段 done 标记的 hour 目录直接跳过**"。所以同一份 gzip 可以被 PT/SFT/RL **各自独立扫一遍**，三阶段 done 标记在文件名上互相不冲突。

### 5.3 数据来源差异（v12_new vs 主流程）

| 对比项 | v12_new 三阶段 | 主流程联合 PT |
|-------|---------------|--------------|
| 数据路径 | `/mnt/video.rank.s101/` | `/mnt_onerec_model/corpus/video.rank.s101.pos_neg/` |
| 是否预处理过 | ❌ 原始曝光日志 | ✅ pos_neg 已做 `check_line` 过滤（删 77% 无交互） |
| 列数 | 131 | 131（同结构，因为 pos_neg 是过滤而非加列） |
| 行级 `check_line` 过滤 | ❌ **没有** | ✅ 有 |
| 物理删行 | 在 parser 里做 | 在 corpus 预处理时做 |

> v12_new 把 main 分支"先 corpus 预处理 + 训练时 PT/SFT 各自过滤"两步合一，全压在 parser 里做。代价：每 step 进 parser 的样本数更多（特别是 PT），筛掉更多。

## 7. 与主流程样本构建的关系

| 对比项 | v12_new 三阶段 | 主流程联合 PT |
|-------|---------------|--------------|
| 范式 | PT → SFT → RL，三个独立 parser | 一个 parser 联合训练 |
| 行级过滤 | ❌ 无 `check_line` | ✅ corpus 预处理时做 |
| 正负样本拆 | SFT 物理删非正反馈；RL 留 dislike 当负样本 | `expand_neg` 用正样本 shuffle 造中性样本 |

| 中性样本 | 没有专门构造 | `expand_neg` 1:1 造 |
| 损失结构 | 三阶段各自 CE / CE / GRPO | 单条 `ct_loss + rl_loss` 联合 |
